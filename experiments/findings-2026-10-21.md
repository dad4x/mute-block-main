## 1. Timers: Worker vs page vs service worker (set aside)

Full note and raw logs: sibling checkout, `experiments/worker-scheduling/NOTE.md` and `results/`.

- A dedicated Worker hosted by a hidden extension page kept a 1 s timer for 35 minutes: 2,100 ticks, median gap 998 ms, worst 1.016 s.
- The hidden host page's own timer was throttled to about once a minute (worst gap 60 s).
- Messages to the page were answered in 1 ms or less, even while the page's timer was throttled.
- A timer in the dev extension's service worker did not survive the same 35 minutes. The worker had restarted and the timer was gone. When it stopped is unknown.
- Each side ran once. The Worker host was a probe tab, not a real writer host.

## 3. Where a block's time goes (1446 run, 30 blocked items)

- Blocked items: median 2.45 s from tab active to finalize. Already-blocked items: median 1.1 s.
- Median breakdown for a blocked item:
  - Tab open to page load: about 1.2 s. Stays unless tabs get reused.
  - Page load to first click: about 0.9 s. The block routine opens the menu with a fixed 500 ms wait afterwards, and its reopen path waits 250 ms and 500 ms.
  - Clicks and block taking effect: about 0.5 s.
  - Block observed to close probe: about 30 ms. Probe answered in 28 ms.
  - Probe answered to finalize: about 2 ms.
- So a "done" signal from the page would save about 30 ms per item (about 2%). The larger candidate is the fixed 500 ms wait after the menu opens, worth up to about 0.5 s per block (about 20%).
- Concurrency: one tab slot, about 75 finalized actions in 5 minutes.

## 4. Close probes with no reply (1446 run)

- 132 close probes; 21 got no reply (about 16%).
- 13 of the 21 were to tabs already gone when probed. Harmless.
- 8 of the 21 were to profile tabs still loading. The probe came before the content script was ready.
- Reply times for the no-replies: 1 ms to 747 ms. Fast failures, not timeouts.

## 9. Writer design (sibling checkout, branch `worker-writer-design`)

- The decision (2026-10-20, owner) moves the write door and resident state into a dedicated Worker, hosted by an extension page. The service worker becomes transient.
- Only a location preference and a pure policy module are built. The write path still runs in the service worker.
- Coupling check in this repo (1446):
  - Storage: 5 direct storage calls in the service worker. Most storage goes through an adapter, so the write door can move with modest work.
  - Tabs: 104 direct tab calls in the service worker. A Worker can't make these, so each needs a page proxy.
  - Timers: 31 timer calls in the service worker.
- What the Worker would and wouldn't fix:
  - Would: scheduling independent of page throttling; service-worker restarts no longer wipe resident state; storage-side serialization moves off the service worker's thread (not measured here).
  - Would not, by itself: the waits. The design's own note says the same queue keeps the same waits. The lock must never span tab waits.
  - Firefox: untested (no offscreen host; content scripts lack `storage.session`).

## Lock-hold baseline (planned, not run)

Question: how long is the single worker's write path held per operation on the current build, and how much of that is waiting on tabs? The writer design (section 9) depends on this answer; the 1.6.1397 waits in the design note are too old to use.

Protocol (needs the owner's go-ahead, and the queue paused for the baseline):
- Per representative operation (block, already-blocked, settlement, enqueue), split the time into: queue wait, CPU preparation, tab API time, durable write, session publication, and completion to the next action.
- Source: the recorder already holds `storage-write` elapsed times and the activation (`persisted`) and finalize records. Add the missing split points as recorder fields first, then take one 5-minute run.
- Comparison to make: how much of each operation's time falls inside the write path, and how much of that is a tab call. A tab call held inside the write path is the thing the writer design must keep out.
- Existing data (1446 run, for orientation only): storage writes average 223 ms when large and 74 ms when small. Settlement writes average about 222 ms.
- Not run. Nothing has been changed for this measurement.

## Recovery B: rebuild a torn checkpoint manifest from the worker's copy (design, not built)

Parked item 1 in the defer pile. Owner said to do it (21 Oct), and this is the design for that. One decision is open (see the end).

Where it sits: when hydrate finds that the active checkpoint's manifest disagrees with the disk metadata, the loader already tries one recovery. It takes the session mirror's copy of the manifest and its shards, and uses it only if that copy matches the metadata (identity check, then hydrate, then the state-hash check). If the mirror copy is missing or fails any check, the load fails closed: the queue stops, and the mismatch is recorded with both fingerprints.

Proposed Recovery B: a second source, the worker's own copy of the checkpoint state, tried after the mirror copy fails. The rebuild does the following.
- It takes the resident state, encodes it as the sharded checkpoint, and compares the result with the metadata's checkpoint. The check is the same one the mirror copy must pass.
- It writes only the manifest and shard records for the active slot, and only when they match the metadata. It never writes the metadata, so the risk that was parked is gone: the metadata is not replaced, and no compare-and-set is needed. The records written are the ones the metadata already vouches for, by state hash.
- Recorded like the mirror recovery, with both fingerprints, so it is visible in the recorder.

What it does not cover:
- The worker's own copy exists only while the worker is alive. A mismatch found on startup has no worker copy, so Recovery B does nothing there, and the load still fails closed. This is the limit the owner has to accept or reject.
- Writes during recovery go through the same storage write as any other checkpoint write, so the queue is paused for the rebuild.

Tests needed: a torn manifest with a matching resident state (rebuilt, queue continues); a torn manifest with a resident state whose hash does not match the metadata (refused, fails closed); no resident state (fails closed, as today); the metadata is never written.

Decision for the owner: (a) build it for live sessions only, as above, or (b) first find a source that survives a restart (for example, a copy written to the session mirror at each checkpoint), which changes the write path and needs its own design.
