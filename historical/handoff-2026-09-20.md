## What shipped (all deployed, live-verified)

1. **`kickQueuedWorkAfterSlotFreed` fan-out fix (1.6.1276)** — this function
   unconditionally fired three 100ms-delayed fallback wake-ups
   (`scheduleQueuedWorkContinuation`, `scheduleCoordinatorQueueResume`,
   `scheduleCoordinatorReconcile`) on every slot-freed event, on top of an
   immediate fast-path call that already does the targeted work in the
   common case. Changed it so the three fallbacks only fire when the fast
   path is deferred (busy) or resolves without `changed: true`. **This was
   the single biggest win of the whole session** — live-verified handoff
   gaps dropped from 60-180s+ (yesterday's baseline) to ~5s, per-block time
   to ~3.5s, immediately after a reload cleared stuck state. Degraded back
   toward the old numbers once the batch had been running a while under
   real load (see "still open" below) — the fix helps, but the deeper cause
   is the full-queue-scan problem, not this fan-out alone.
2. **`profileAction.reallyBlocked`/`alreadyBlocked` stat fixes, in two
   passes:**
   - First pass (1.6.1277): the stat was *undercounting* — only recorded
     on the one code path where `reduceJobEvent` cleanly accepted a
     terminal transition; two sibling branches in the same function
     (`swCoordinatorProgressReducer.js`) also produce genuine terminal
     blocked/already-blocked outcomes (a stale-retry rejection fallback,
     and the row promoted-to-succeeded correction path) and never called
     the stat function. Added the same stat call to both.
   - Second pass (1.6.1279): that fix then *overcounted* ~14x (654
     increments vs. only 45 genuinely-new terminal rows in one 98-minute
     epoch) — a row cycling through a terminal-producing transition
     multiple times (the still-open stale-attempt-handler bug makes this
     common) got counted every time. Fixed with a row-identity `Set` guard
     (keyed by `runId::href`) alongside the existing per-transition
     `WeakSet` dedup.
3. **Dashboard: scan-cost + event histogram panels (1.6.1278)** — two new
   collapsible panels, horizontal bar charts, one row per occurrence type,
   sorted by count descending. Scan-cost reads new `scan.<location>.calls`/
   `.items` counters (see below); events tally straight from the existing
   flight-recorder buffer, no new sw.js instrumentation needed.
4. **Histogram bar zero-alignment fix (1.6.1279)** — the label column had
   no fixed width, so each row's bar started at a different x-offset.
   `.histogram-label` is now `flex: 0 0 150px` / `width: 150px`.
5. **Event histogram trend coloring (1.6.1280)** — rows go green when a
   label's count is same-or-down since the last refresh, red when
   increasing, neutral for a label seen for the first time. Scan-cost
   histogram unaffected (trend is an optional per-row field, not baked into
   the shared render helper).

## The real root cause, now confirmed with hard numbers

Live epoch metrics (98-minute run, before Part A was attempted):

```
scan.classifyCoordinatorExecutorState.calls  = 3704   items = 6,874,624
scan.runCoordinatorExecutorApplyPhase.calls  = 3581   items = 6,646,336
scan.makeCoordinatorAuthorityProjection.calls= 6357   items = 11,798,592
```

~1856 items touched per call, every single time, across all three —
confirms every reconcile/pump tick (and every single-row authority mutation,
since `makeCoordinatorAuthorityProjection` deep-clones the *entire* queue on
every call) does a full scan/clone of the whole queue, not just the ~200
rows that are actually still queued/active. This is the dominant cost
behind both the handoff-latency problem and the write-queue backlog you
saw (85 alerts, 1290 view writes, 9.4% storage-update timeout rate this
epoch) — the write backlog is very likely the *same* root cause (the
authority projection clone is O(queue size) on every write, and the queue
is 1856-and-growing), not a separate bug.

## Useful things learned this session (avoid re-deriving)

- **The one true choke point for every durable queue-row mutation** is
  `coordinatorAuthority.apply()` / `.applyWithinStorageUpdate()` ->
  `applyLocked` (`sw.js`). Every other "wholesale queue replace" path
  (`absorbPersistedSnapshot`, WAL replay/recovery, raw-queue fallbacks) is
  a full reload, never a per-row merge.
- **`queueRuntime.rebuildQueueOrder` is called from exactly one place**
  (`refreshResidentCoordinatorAuthorityState`, gated on `changed===true`)
  — ordinary single-row `apply()`/`applyWithinStorageUpdate()` calls never
  refresh it, which is why `getOrderedQueueItems` needs its own
  defensive "leftover keys" fallback scan.
- **`shared/js/swqueueRuntime.js` is explicitly documented (file header) as
  not allowed to interpret queue *status*** — it's volatile runtime/tab
  bookkeeping only. Any "queued-only index" idea belongs on the
  authority/projection side (`sw.js`), not inside that module.
- **The `removedRows` + `persistCoordinatorAuthorityQueueWalBatchMutation`
  pattern** (four existing call sites, e.g. `retryCoordinatorFailedItems`)
  is the proven way to move a row out of the live queue: build a queue
  copy with the key deleted, push `{rowKey, previousRow, operationKind,
  reason}` into `removedRows`, batch-persist, then `coordinatorAuthority.hydrate()`
  to resync rather than hand-rolling the in-memory projection update.
- **This session's chrome-dev extension ID differed from
  `tools/cdp/lib/cdp.js`'s hardcoded `DEFAULT_EXTENSION_ID`** — always
  confirm via `curl http://127.0.0.1:9222/json/list` before trusting a
  CDP tool's default.
- **The flight recorder is in-memory only and resets on service-worker
  idle/restart** — capture traces promptly (`node tools/cdp/flight-recorder.js
  --extension-id <id> --row-key <profile-url>`) or the evidence is gone.
  The durable sharded progress store (`mbProfileNukeProgressShard.N`) 
  survives restarts; `mbProfileNukeProgressView` does not (it's a
  truncated aggregate that can silently omit rows).
