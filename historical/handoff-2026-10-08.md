## What shipped (all deployed to chrome-dev, live-verified)

1. **Executor-apply scan-bound (1.6.1377)** — `runCoordinatorExecutorApplyPhase`
   had its own unbounded loop over the full queue (paying cheap-but-nonzero
   per-item cost for every row) separate from `classifyCoordinatorExecutorState`'s
   already-bounded front-of-queue scan. Capped it at
   `COORDINATOR_RECONCILE_ACTION_BUDGET` (25) queued rows per tick. Live:
   SECS/REAL BLOCK dropped from ~26-38s to ~9-12s.
2. **Content-queue-index sharding + fill-timeout-refresh scoping (1.6.1378)** —
   `getContentPageCoordinatorState` was reading the entire
   `COORDINATOR_CONTENT_QUEUE_INDEX_KEY` blob (scales with queue depth) on
   every content-script poll. Sharded by profileHref (additive — old
   monolithic key untouched for back-compat). Also scoped the
   fill-timeout authority refresh inside the same function to known
   activation hrefs instead of an unscoped full-progress-shard fetch.
3. **Fast-executor resume-storm coalescing (1.6.1379)** — a burst of
   distinct reactive triggers (slot-release, active-transition,
   queued-authority-enqueue, etc.) could each independently call
   `runCoordinatorQueueExecutorFastPath` within milliseconds of each
   other; live telemetry showed 13 back-to-back calls, 45-72s each, all
   but the first finding nothing left to do. Added a cheap (no storage
   I/O) in-memory fingerprint check: if a pass completed within
   `COORDINATOR_FAST_EXECUTOR_RECENT_NOOP_COOLDOWN_MS` (2000ms) and
   nothing's changed since, reuse that result. Confirmed live: storm cut
   from 13 calls to 2.
4. **WAL checkpoint gzip compression (1.6.1380)** — the two paired queue-WAL
   checkpoints (`mbCoordinatorQueueWal.checkpoint.A`/`.B`) were ~9.7MB
   each, uncompressed, ~69% of the extension's entire storage footprint.
   `walSnapshotStore.js` already had a fully-tested pluggable codec
   mechanism, never wired to a real codec. Added `fflate` (sync
   gzip/gunzip, zero deps) as a direct dependency, threaded a
   `COORDINATOR_QUEUE_WAL_SNAPSHOT_CODEC` through every checkpoint
   read/write call site in sw.js plus one in `swCoordinatorQueueWal.js`
   (`verifyAppendedCoordinatorQueueWalReplay`, which runs on every WAL
   append). Shipped as a single deploy, not a staged rollout — every
   checkpoint already carried a `codec`/`encoding` tag that the read path
   already fell back on for old-format data, so there was no actual
   backward-compat gap to wait out. Confirmed live: 14.8:1 compression
   ratio, storage footprint 28MB→12.4MB.
5. **Franklin Veaux embed-misclassification fix (1.6.1381)** — a genuine
   contributor (Franklin Veaux) got queued for mute-block because his
   answer to an unrelated question was embedded/quoted in a troll-patrol
   space's post; the scanner picked up the embedded answer's author
   byline as a candidate. This was the *third* occurrence of the same
   bug class (two earlier fixes, 2026-09-25 and 2026-09-27, patched
   different collectors but missed this one). Fixed
   `getSpaceFeedProfileLinkCardRoot` (the asset-space "profile card"
   scanner) and, after auditing for siblings per the user's request,
   `getSpaceFeedPostContentScopes` (closes two more latent,
   not-yet-triggered instances in the main `dom-profile-link` loop and
   the `text-profile-url` fallback) — both now exclude
   `SPACE_FEED_EMBED_SCOPE_SELECTOR` regions. See the dedicated memory
   file for the full incident timeline and a "lesson for next time" note
   on verifying a report is live vs. already-fixed-but-stale-looking.
6. **Per-reason tabGetFailed/tabGetTimedOut breakdown (1.6.1382,
   diagnostic only)** — broke the flat counters down by caller `reason`
   across all 13+ callers of `getQueuedExecutorTabStatusWithTimeout`, to
   find which one actually drove the aggregate failure ratio instead of
   guessing.
7. **sweepStaleQueuedTabs tab-get parallelization (1.6.1383)** — the
   breakdown fingered `stale-queued-tab-sweep` as the dominant timeout
   source (19/50 timeouts in one window, 100% of its own failures being
   genuine timeouts vs. ~37% for the next-largest caller). Root cause:
   `sweepStaleQueuedTabs` looped over active tabs sequentially, one
   `chrome.tabs.get()` at a time, each with its own 2500ms timeout — a
   slow/hung lookup for tab N delayed even starting the lookup for tab
   N+1. Fixed by prefetching all tabs' statuses via `Promise.all`, but
   **only when there's more than one tab needing a check** — the first
   unconditional-`Promise.all` attempt broke 5 unrelated fake-timer tests
   because even an empty/single-item `Promise.all` costs one extra
   microtask tick that those tests' fixed tick sequences had no slack
   for. Confirmed live under a clean environment (no confounding load):
   tabGetTimedOut total dropped from 128 to 4 in one window,
   `stale-queued-tab-sweep` specifically from 48/19 down to 2-3.

## Still open

1. **SECS/HANDOFF's residual elevation — current best lead: worker-window
   single-tab serialization.** With `tabGetTimedOut` now negligible, the
   clearest remaining signal is `actionSurface.workerWindow.openSkippedBusy`
   running close to or above `job.tabOpened` in the same window (41 busy
   skips vs. 34 opens in the last clean check) — the "worker window" used
   to open profile tabs in the foreground can only hold one tab at a
   time, and journal entries show retries costing 7-8s each and one
   successful open taking 16.8s end-to-end. This is the same mechanism as
   the already-documented, already-deferred "Worker-window foreground
   race" issue (see that memory file) — not a stuck/orphaned tab this
   time, just genuine contention from real throughput. **Not yet
   investigated for a fix** — explicitly deferred as a bigger
   architectural question (candidate: parallel-load/serial-execute model)
   rather than patched blind under this session's time pressure. Natural
   next step if picked back up.
2. **Confounding-load lesson, not a bug:** one check this session showed
   `stale-queued-tab-sweep` apparently regressing (48 timeouts) and
   storage ops ballooning to 9.9-13.6s — traced to the user having ~1227
   unrelated CDP targets open (44 browser tabs + ~1000 ad-sync iframes),
   not a code regression. Before reading any per-reason counter as a
   verdict on a fix, sanity-check `target-summary.js`'s `totalTargets`
   first.
3. **`node test/swSynthetic.test.js` (no args) silent hang** — pre-existing,
   confirmed unrelated to this session's work (reproduces on `git stash`),
   still not root-caused. Workaround: `--range=1:490` plus `--filter=` for
   anything past that boundary. See
   `project_swsynthetic_silent_hang_2026_10_07.md`.
4. **`resetMetrics()` / "Clear All Stats" button throws**
   `TypeError: Cannot read properties of null (reading 'view')` (caught,
   logged as a WARN, non-fatal) — noticed in passing multiple times this
   session, never investigated. May mean the metrics reset doesn't fully
   take effect. Worth a quick look next time that button is used.
5. **pendingPosts/nukedPosts scoping (`terminalSettlement.load`/`.derived`)**
   — deferred earlier this session as too risky to rush: `mbSpacePendingNukedPosts`
   is keyed by `postKey`, not profileHref, with a many-to-many
   relationship (`remainingUrls` can span multiple hrefs) and no existing
   reverse index. Not part of the final chase-list fixes; would need a
   dedicated design session.
