## What shipped (7 items, all deployed)

1. **Button overlap** ("Mute Block Close"/"Mute Block" render stacked) —
   `resetProfileButtonRail()` now fires on same-tab profile-to-profile
   navigation too, and the dedup sweep in `getOrCreateProfileButtonRail`
   runs unconditionally instead of only on the fresh-create branch.
2. **"Really blocked" undercounting** — `close-if-blocked`'s response now
   carries `blockAttempted` from the tab's own in-memory state instead of
   waiting on the durable milestone.
3/4. **Long handoffs + write-queue-backlog alerts** — chunking a large
   space-feed enqueue moved from sw.js (one tight awaited loop, no real
   yield between chunks) to content.js (`sendCoordinatorEnqueueChunked`):
   each chunk is now a separate message, so the gap between chunks is a
   real macrotask, giving other writers an actual turn. The "Nuke 'Em"
   button now shows `Queueing... N of M` as chunks land.
5. **Batch-enqueue button stuck on "Nuking..."** — 15s message timeout +
   90s durable-summary poll fallback, generalized into the same chunked
   helper as items 3/4.
6. **Write-queue backlog recurred under real execution load** (a
   *different* mechanism from 3/4) — the WAL checkpoint-switch was
   waiting in the same FIFO as ordinary writes; under real concurrency it
   could wait behind the backlog for tens of minutes while the WAL tail
   grew unbounded, making every read progressively slower (self-
   reinforcing spiral — one checkpoint in 3.4 hours, tail at 493 vs. the
   ~128 it should switch at). Took it out of the shared queue entirely:
   `scheduleCoordinatorQueueWalCheckpointSwitch` now just marks a switch
   *due*, and `maybeRunDueCoordinatorQueueWalCheckpointSwitchInline` drains
   it as a prefix step on whichever ordinary write runs next — still
   fully serialized (runs inside that write's own exclusive turn), just
   no longer needing its own queue position. **Live-verified**: checkpoint
   ticked to 1 within ~6 minutes of resuming, tail stayed in the 128-136
   range instead of ballooning.
7. **Retry loses which attempt actually blocked it** — a heavily-retried
   item (confirmation lost on an earlier attempt, forcing a retry) landed
   as `already-blocked` even when active-to-terminal duration matched a
   real click-through. New durable field `item.initialBlockedState`,
   captured once from whichever attempt's tab first observes it and never
   overwritten by a later retry; `classifyBlockConfirmationFromItem`
   prefers it when known. **Live-verified partially**: post-fix epoch's
   retried items both had short, genuinely-instant durations (consistent
   with correct classification) — haven't yet caught a long-duration retry
   to confirm it now lands as `blocked` instead of `already-blocked`.

**Bonus, unnumbered**: removed the dashboard's 5-second poll
(`resumeCoordinatorQueueResume` timer in coordinator.js) that was actively
driving `kickCoordinatorQueueResume` just because a dashboard tab was
open, regardless of whether anything had changed. Note
`coordinator.html#worker-window` runs the same bundle, so two dashboard-
family tabs open meant two independent pollers. The SW's own alarm-based
scheduling doesn't depend on this. The explicit Start/Resume button
(a real user action) is untouched. **Not yet live-verified** — just
deployed; extension reload closed the open dashboard tabs (normal Chrome
behavior for unpacked-extension reload, not specific to this change).

Full suite green at every step (869/869, then 868/868 after removing the
one test that exercised the deleted dashboard-poll mechanism).

## Open, not yet started: the deeper "event-driven vs. polling" question

While tracing why handoffs (one item's tab closing → the next item's tab
opening) took 60-100+ seconds even after items 3/4/6 landed, found via the
flight recorder that a single handoff involves **~10 separate reconcile/
fill passes** over ~10 seconds before the system commits to actually
opening the next tab — most bouncing off `queued-activation-in-flight` or
`no-tab-opened` ("someone else already has this slot, try again shortly"),
not one direct "slot freed → open next item" handoff. The dashboard's 5s
poll (just removed) was one contributor, but far from the only one — real
events (`queued-tab-release`, `terminal-progress-continuation`,
`active-transition-fast-detached`, etc.) also each trigger a *broad
re-scan* rather than a *targeted* handoff, and under concurrency
(`executorMaxConcurrent: 3`) several land close together and mostly
re-confirm "not yet."

The user's framing: they expect the system to be event-driven in the
normal case, with periodic checks only as a fallback — not periodic
checks (or broad re-scans triggered by any event) as the primary
mechanism. This is a real architecture question, bigger than anything
fixed above, and hasn't been scoped or started. Next step if picked back
up: trace one clean handoff end-to-end (the Daniel-Mackintosh-3 trace in
the worklist/conversation is a good starting example) and figure out
whether "targeted handoff" (specific freed slot → specific waiting item,
no broad re-scan) is achievable without the kind of priority/reordering
mechanism the user has twice now said they don't want for business-item
ordering. This is squarely about *reducing redundant re-evaluation*, not
about reordering which item goes next.

## Useful things learned this session (avoid re-deriving)

- **`test/lib/swHarness.js` runs sw.js in a `vm` sandbox with fully fake,
  manually-ticked timers.** A real macrotask yield (`setTimeout`) added to
  sw.js code binds to that fake clock in tests, hangs forever if nothing
  ticks it, and since nothing else keeps Node's real event loop alive, the
  whole test process silently exits(0) at that point — no failure ever
  reported, just fewer "ok" lines than expected. This is why the item 3/4
  fix moved chunking to the *poster* (content.js) instead of adding a
  timer-based yield inside sw.js's write chain.
- **The checkpoint-switch's `metricStorageSet` is a blind overwrite**, not
  a compare-and-swap — no version/ETag check against what's currently in
  storage. This is *why* it can't safely run fully unserialized against
  concurrent WAL mutations (would reintroduce the "missing-segment" WAL
  corruption class of bug this project has hit before) — confirmed before
  implementing item 6's fix, not assumed.
- **`mbCoordinatorQueue` (the raw queue key) no longer exists** — WAL-only
  now. Use `mbCoordinatorQueueView.items` for any CDP-based inspection
  (per-item `outcome`, `retryCount`, `activeAt`/`terminalAt` are all
  there); `mbProfileNukeProgressView` is for **legacy/manual actions only**
  and will return misleading nulls/stale data for coordinator-queue items
  — don't use it for classification debugging (cost real time this
  session before catching it).
- **Version bump before every rebuild+reload** is now a standing rule
  (saved to memory) — `package.json` + `manifests/chrome.json` +
  `manifests/firefox.json`, all three, by hand. The `reload:chrome-dev`
  tool's `before`/`after` version fields are the actual confirmation a
  reload picked up new code; `reload: {ok: true}` alone only means the
  CDP call succeeded, not that anything changed.
- **`chrome://extensions/` tabs left over from a previous failed reload
  attempt can wedge the next reload** (`Runtime.evaluate` timeout on the
  `chrome.developerPrivate.reload` call). Fix: close the existing
  `chrome://extensions/` tab via `curl .../json/close/<id>` and retry —
  worked cleanly both times it came up this session.
- **Extension reload closes open dashboard tabs**, doesn't reload them in
  place — expect to have to reopen `coordinator.html` after every deploy.
