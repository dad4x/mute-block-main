• From the live metrics, I’d say:

  Recovery is not currently the normal correctness mechanism, but recovery-shaped orchestration is still
  normal operation.

  Evidence from the current sample:

  - job.completedOnlyAfterRepair = 0, so terminal completion is not visibly depending on repair.
  - repair.requested = 5181, but only repair.changed.queue = 8 and repair.changed.runs = 8; most repair is
    polling/no-op reconciliation.
  - repair.noop = 4782, which is far too high for something that should be exceptional.
  - pump.requested = 814, pump.changed.* = 121, so pump yield is only about 14.9%.
  - nudge.acceptance = 77.5%, which is comparatively healthy. Nudges are not the main smell right now.
  - wakeupsPerJob = 58.2, though that ratio is rough because job counters span mixed run history.
  - Storage is still the big problem: 1.27 GB cumulative overlapping writes against only 3.2 MB live
    storage, with saveCoordinatorStateCalls = 1272.
  - Storage update timeout/fallback/abandon rates are all around 24%, mostly during storage get.

  So the present shape is: normal work still leans on repeated load/recompute/save, pumps, and repair ticks
  to converge. But actual terminal truth does not appear to require repair as the path of record.

  That means the other refactor is aimed at the right layer. The next threshold to watch is whether, after
  the authority refactor, these move:

  - repair.requested / job.enqueued drops sharply.
  - repair.changed.* remains rare.
  - pump.changed.* / pump.requested rises.
  - saveCoordinatorStateCalls and full snapshot bytes fall.
  - storageUpdate.timeout.* falls.
  - job.completedOnlyAfterRepair stays near zero.

  If those improve, repair remains recovery. If repair requests stay high and full-map writes stay high,
  then yes, the system is effectively using recovery/reconciliation as its ordinary scheduler.
