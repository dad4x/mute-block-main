[2026-09-16, later same night: write-queue-backlog investigation, separate
from the 8 items above]

The live batch developed severe write-queue-backlog stalls (up to 265-286
SECONDS for the oldest pending write, thousands of storage timeouts, and
the reallyBlocked/alreadyBlocked epoch counters running 2-9x ahead of real
completions) on three separate occasions after the segmented-WAL hydrate
race fix shipped. Root cause each time: an unbounded per-item loop doing
real awaited storage/tab work, entirely inside one
enqueueSpaceFeedStorageUpdate critical section, so a large batch (the
common trigger: resuming a long-paused queue, which lets a backlog of
terminal-eligible/milestone-bearing rows accumulate) holds the single
serialized write queue's head for as long as the whole batch takes,
blocking everything else queued behind it.

Three confirmed instances found and fixed (all in shared/js/sw.js, same
chunk-and-reschedule shape as COORDINATOR_ENQUEUE_CHUNK_SIZE's original
fix):
  1. reconcileCoordinatorStorageLocked's progress-reconcile tail (tab-query
     loop) -- capped at COORDINATOR_PROGRESS_RECONCILE_CHUNK_SIZE (25) via a
     rotating resume-key window (not a naive first-N, which would starve --
     queue key order is stable, so the same already-resolved rows would eat
     the whole budget every tick and the rows further back would never get
     reached).
  2. settleTerminalCoordinatorItemsLocked's href list -- capped inside the
     function itself (protects every caller, including content.js's
     space-feed reconciliation, which was sending an unbounded pending list
     to the one caller-side cap that existed before).
  3. applyCoordinatorRowEvents, fed by coordinatorJobMilestonePendingRecords
     (a global accumulator explicitly designed to pile up milestone records
     from many tabs while the coordinator is busy, then burst-flush
     everything in one shot once the busy-gate clears) -- flushCoordinatorJobMilestones
     now drains COORDINATOR_MILESTONE_FLUSH_CHUNK_SIZE (25) records per
     iteration of its existing while loop instead of grabbing and clearing
     the whole accumulator at once.

Important open question, not resolved: fix #1 lives behind
reconcileCoordinatorStorage, which turns out to be reachable ONLY via a
manual, explicit 'reconcile-coordinator-storage' user-initiated message
(gated by userInitiated === true, checked directly in swBootstrap.js) --
there is no automatic/scheduled caller anywhere in the codebase. Neither of
us knowingly triggered that action during the incidents, so fix #1, while a
real bug, most likely did NOT cause what was observed live. Fix #3 is fully
automatic (fires on ordinary tab milestone reporting) and is the better
mechanistic match, but the literal 'terminal-progress'/'direct-progress'
reason strings seen in the live stall messages were traced to a *different*,
always-single-href call site (recordCoordinatorJobProgressRecords's
non-deferred branch), not to fix #3's code path -- so even that match isn't
clean. Net: three real bugs fixed, all independently worth having, but no
single one has a fully confirmed causal link to the specific incidents
observed. If backlog stalls recur even with all three fixes live, that's
the signal this is actually a throughput/backpressure problem (many small,
individually-fast operations arriving faster than the serialized queue can
drain them after a resume) rather than any one unbounded batch, and needs a
different class of fix (e.g. rate-limiting how fast new critical-section
work can be enqueued after a pause, not just capping individual batch
sizes).

Resumed the paused queue (5 remaining + soft/hard-fail retries queued) and
within ~3 minutes the reallyBlocked/alreadyBlocked epoch tiles were reading

Root cause, confirmed against live storage.local data (not just log
inference): scheduleTerminalProgressContinuation (moved to
swCoordinatorJobMilestoneBookkeeping.js in decomposition Slice 40) fires
three continuation mechanisms -- scheduleQueuedWorkContinuation,
scheduleCoordinatorQueueResume, and a direct runCoordinatorQueueExecutorFastPath
call -- unconditionally on every successful terminal-progress settlement,
with no in-flight coalescing. Its sibling three lines up,
scheduleTerminalProgressSettlement, already does exactly this coalescing
(a terminalProgressSettlementPromises Map keyed by href) -- this one didn't.
The two scheduler calls self-throttle already (scheduleCoordinatorQueueResume
has its own alarm-coalescing scheduler; scheduleQueuedWorkContinuation has
isKeyedThrottleCoalesced), but the direct runCoordinatorQueueExecutorFastPath
call did not, so every settlement could spawn another full executor pass,
which (for a handful of specific rows -- Vivian-Christian-21, Vivian-Robert-25,
Victoria-Lane-214, Wills-Alira-1 this run) re-discovered the same
already-eligible row via the "queued-authority-without-executor-surface"
self-settlement path (sw.js's runCoordinatorExecutorApplyPhase,
terminalRecordSettlesQueuedAuthority check, ~line 15782) and re-settled it,
spawning more continuations. Confirmed via epoch counters:
terminalProgress.queuedSettlement.save fired 167 times in ~10 minutes vs.
5 for the normal single-row terminalProgress.save path -- i.e. this specific
self-settlement loop, not live tab progress reports, was the amplifier.

Not data loss: current storage.local confirmed Vivian-Christian-21 and
Victoria-Lane-214 both correctly landed status:"succeeded". Wasted,
redundant writes amplifying write-queue backlog and epoch counters, not
corruption.

Separate, NOT fixed, real finding from the same investigation: while
tracing why the row kept re-reading as "queued", found that
mbCoordinatorQueueView (the durable, denormalized queue snapshot the
dashboard/popup/CDP tools all read directly via chrome.storage.local,
distinct from both the WAL and the coordinatorAuthority module's own
in-memory resident projection) can silently diverge from the WAL under
load: its write is a separate, non-atomic storage.local.set inside
persistCoordinatorAuthorityQueueWalMutation (sw.js ~line 6806-6837) that
can fail independently of the WAL append it's supposed to mirror, with only
a best-effort scheduleCoordinatorReconcile(1000, {reason:
'queue-wal-projection-failed'}) as catch-up -- itself competing for the
same backlogged write queue. Caught live: Wills-Alira-1 had a flight-recorder
entry claiming a persisted terminal-settlement WAL write, but its
mbCoordinatorQueueView record was untouched (status still "queued",
updatedAt == original queuedAt) at the time. This is a known, tested
degrade path (see test/*.test.js: "terminal job progress reports durable
terminal queue despite projection save failure") rather than an unhandled
crash, but there's no guaranteed reconciliation deadline -- a view row can
stay stale indefinitely if the retry keeps losing the race under sustained
backlog.

Raised while discussing this: why does mbCoordinatorQueueView need to be
persisted (chrome.storage.local) at all, rather than computed on demand?
The only two real justifications found: (1) chrome.storage.local writes
push storage.onChanged to every open extension page for free, which is
how the dashboard/popup get reactive updates without an open message port;
(2) it gives instant reads to short-lived/lightweight contexts (popup, CDP
debugging tools) without a message round-trip that has to wake a possibly-
idle service worker and wait for a live WAL-replay-derived answer.
"Durability across restarts" is NOT a real justification -- the WAL is
already the durable source of truth and the SW rehydrates from that, not
from the view, on cold start.

A real alternative worth considering: drop the persisted view entirely,
have readers ask the SW directly (chrome.runtime.sendMessage, which wakes
it if asleep) for a freshly-computed snapshot, and have the SW broadcast a
change notification to currently-open pages on mutation instead of relying
on storage.onChanged. That removes the second non-atomic write and the
whole divergence class of bug outright, at the cost of a message round-trip
per read and losing push-updates to pages that aren't open yet (acceptable --
they'd just ask fresh on open). This is a real simplification, not just
cleanup, but it touches every consumer of mbCoordinatorQueueView (dashboard,
popup, all the CDP tooling built up this week) and deserves its own careful
pass rather than being folded into a bug-fix session. Worth scoping properly
next time before touching it.
